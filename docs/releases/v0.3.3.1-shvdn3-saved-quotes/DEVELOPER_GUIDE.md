## Complete requested behavior

Repair coverage (#27, implemented first): fixed quote = max(existing service base plus existing expertise premium, estimated reserved parts acquisition plus allocated billable mechanic labor). Physical, background and remote paths share the calculation. Existing supplier procurement and payroll are not charged again. Universal/filter/brake/diagnostic parts use their actual dedicated-first/universal-fallback allocation, with two units for physical brake jobs. Quotes and source allocations stay fixed after acceptance, including when wages, equipment or configuration change later.

The inventory has counts, not purchase lots. Default unit estimates $125/$113/$200/$157 conservatively cover current express acquisition before discounts. Optional Settings.ini [Pricing] UnitCostEstimateUniversal, UnitCostEstimateFilters, UnitCostEstimateBrakes and UnitCostEstimateDiagnostics are nonnegative long estimates; missing/negative values select the source fallback and zero is deliberate. No historical acquisition cost or profit guarantee is invented. Labor uses mechanic wage/period and predicted billable repair duration, including existing wage bonus/specialty and speed effects. Walking, waiting, stalls, idle payroll, crash rework and later wage/config changes are outside that fixed billable estimate. Old promises remain old promises, even when below a newly configured estimate. RepairPricing.v1.csv is a separate completion audit; old customer CSV schemas are unchanged.

Manual parts sales (#25, implemented second): Business Management → Inventory & Suppliers → Parts Sales offers four stocked one-unit actions with quantity/availability/fixed-estimate preview. A fresh confirmation sells one unreserved selected unit, with shared input debouncing plus same-frame protection, no employee markup and no passive customer or mission. Pending deliveries/cargo and exact repair reservations are excluded. Cash/Revenue increase once; retail PartsSalesRevenue is separate from customer repair revenue and PartsSalesUnitsSold tracks units. Both additive [Business] keys default to zero. A failed atomic save rolls back all sale changes. Supplier invoices, payroll and earned delivery-box visuals are untouched. PartsSales.v1.csv is separate.

Pallet placement (separate focused branch): up to nine earned boxes using cached model min/max bounds; prefer centered partial layers and 4–4–1, rotate with the saved heading and use the actual grounded pallet prop as world origin. Alternate fitting footprints and a 90-degree box turn are bounded fallbacks. Smaller footprints can make taller stacks; actual model/collision/MLO behavior and fallback realism await GTA testing. Invalid bounds fail placement before any new invoice/stock commit. Partial-layer rebuilds reposition owned props and a failed lower parcel hides unsupported upper owned visuals. Legacy mask gaps compact only visible rank from the bottom without inventing old boxes or changing saved masks/counts/capacity. Saved pallet positions and wholesale financial logic remain unchanged. Geometry is cached by at most eight model pairs and is not recalculated per frame.

Manager wages (separate focused branch): Business Management → Expenses & Bills → Pay Manager Wages shows the existing outstanding invoice and calls the same PayInvoice helper as Manager Profile. It pays separately from Pay All Bills, excludes the manager's own payroll rebate and preserves unrelated liabilities. No new wage schema or accrual was added. A failed individual payment save restores due, money, expenses, savings and invoice ages; repeat confirmations and both orders of individual/Pay All payment cannot pay the same invoice twice.

## Accepted repair reload behavior

Before this followup: the foundation persisted financial totals but cancelled runtime customer/remote objects on reload; accepted quote history and exact allocation were lost. After: one additive bounded RepairPromisesV1 journal snapshots accepted quote data together with the ordinary business ledger. No GTA entity handle or world object is saved. Loading parses data only, retains a deliberately CLOSED shift, creates no entities, gives no income, and never uses file age or UTC elapsed to advance remaining work.

Physical accepted customers return through the existing configuration, proximity, reception, drop-off clearance, model loading and arrival path after the owner reopens the business. They keep order ID, price, cost breakdown, billable duration, exact parts allocation and last-saved work. They must reach the ordinary mechanic work/handoff phase before any payout. Current model/config selection supplies replacement entities, not stale handles. If staff changed, an available current mechanic can perform the existing promise at its fixed price/time. Entity-loss, streaming or close cancellation parks accepted physical work before resetting its worker timer; manager handoff keeps one remote identity rather than a second physical promise. Unaccepted random arrivals are not promised invoices and keep their existing cancellation behavior.

Background and remote promises restore only during positive active unpaused economy processing after reopening. An unavailable mechanic keeps work parked until an eligible current mechanic exists; remote promises wait for a manager. Existing mode rules still apply: background work requires background mode, physical customers require customer service/reception configuration, and remote work retains manager rules. Remaining time is the last saved active-work value; unsaved progress before a hard crash may need to be performed again. There is no offline catch-up. A ready-but-unpaid saved record still waits for a positive unpaused gameplay opportunity; physical work also waits for the normal NPC/vehicle phase.

Pending and respawned quotes reserve exact stock before their NPCs exist, so manual parts sales cannot drain it. Restoration does not consume or bill parts a second time, and handoff snapshots deduplicate the same order identity. Status lists parked order IDs, fixed amounts and remaining active seconds. No user data from older saves can reconstruct quotes that were never saved by any earlier build; those old saves default to an empty journal. The forward persistence guarantee starts with quotes accepted by this candidate.

## Atomic settlement and failure behavior

TrySettleRepair centralizes all three repair payouts. A successful same-directory atomic business snapshot contains both the cleared promise and the one cash/revenue/stock/counter/XP update. On a failed snapshot it restores those fields, the physical Paid flag or remote queue position, and the mechanic's job state. Completion CSVs/notices are emitted only after success. Expense ledgers are unchanged. Physical assignment saves the accepted quote before vehicle tasks or an acceptance notice; if that save fails, assignment and premium are rolled back.

A failed repair commit retries at most once every three GTA game seconds per quote, using wrap-safe Game.GameTime arithmetic; it does not write every frame. Idle completed layouts do no placement calculations. Snapshot I/O is limited to existing save events, explicit actions and accepted/completed job transitions. The journal is bounded to 16 records; new acceptance stops before capacity would overflow. Closing the business parks all accepted routes before resetting workers, without advancing them. OnAborted snapshots promises before owned-entity cleanup, while preserving the original pre-activation abort guard. Startup delay/hold defaults and OnTick time sampling are unchanged.

RepairLedgerStamp binds a nonempty journal to the financial/inventory/job-counter values stored in the same snapshot. If an older build preserves unknown journal keys but changes cash, stock or completed jobs, returning to this candidate stops startup instead of replaying stale payable work. This is a consistency check, not an anti-cheat/authentication claim. Malformed/duplicate/nonfinite records, an unsupported version, too many records or a mismatching stamp throw before callbacks register and before any business save write. Preserve the file and request review or restore a matching full test backup; do not delete keys or silently discard invoices to bypass an error.
